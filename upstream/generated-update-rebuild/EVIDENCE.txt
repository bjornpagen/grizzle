EVIDENCE: an UPDATE that assigns no column a stored generated column reads initializes the table's generation
expressions again for every row, in the per-query context; and the v3 patch, which makes it do so once

Run 2026-11-19 on aarch64-linux (Ubuntu 26.04, gcc 15.2.0, 64 cores), on a box other work kept at load 170-260, so
times are noisy and memory is not. Every build is from a fresh clone of https://git.postgresql.org/git/postgresql.git,
meson, -Dllvm=disabled; the measuring builds -Dcassert=false (debugoptimized), the testing builds -Dcassert=true
-Dtap_tests=enabled. Each measurement runs in its own throwaway cluster (initdb, Unix socket only, fsync=off, jit=off),

1. THE CAUSE, IN THE SOURCE (master 5c06a7ef24c, src/backend/executor/nodeModifyTable.c)
   a. ExecInitGenerated(), line 445, switches to estate->es_query_cxt (477) and, for every generated column, fetches
      its expression with build_column_default() (491: stringToNode() of adbin plus coercion) and, in an UPDATE without
      a BEFORE ROW UPDATE trigger, pull_varattnos() of it (504), to skip a column no UPDATE target column feeds.
   b. When it needs none, "didn't need it after all" (527), it pfrees the array and stores NULL in ri_GeneratedExprsU,
      with ri_NumGeneratedNeededU = 0 and ri_extraUpdatedCols_valid = true.
   c. ExecComputeStoredGenerated(), line 559, which ExecUpdatePrepareSlot() (2185) calls for every row of a table with
      a stored generated column, tests ri_GeneratedExprsU == NULL (581) to decide to initialize, so every row runs (a)
      again. The "Don't call twice" Assert (536) tests the same NULL and so cannot fire.
   d. Nothing frees what (a) allocates until ExecutorEnd.
   The same code is on REL_18_STABLE and REL_19_STABLE, and in the release tags REL_18_0 to REL_18_7 and REL_19_0.
   REL_17_STABLE's ExecInitStoredGenerated() has no such block and always keeps its array.

5. TESTS
   a. The regression test the patch adds (generated_stored.sql, mirrored in generated_virtual.sql) updates several
      rows without touching what g reads, by UPDATE, INSERT ... ON CONFLICT DO UPDATE, MERGE, UPDATE under a
      statement-level BEFORE UPDATE trigger (which reaches ExecInitGenerated() first, through
      ExecGetAllUpdatedCols() in ExecBSUpdateTriggers()), and UPDATE of a partitioned table.
   b. Its kill: master with only the Assert change, Assert(!resultRelInfo->ri_extraUpdatedCols_valid), and not the
      fix, assert-enabled: the core regression suite passes without the new test (no existing test calls
      ExecInitGenerated() twice for one result relation), and with it generated_stored dies:

6. IN THE FIELD (lane FILLMEM, 2026-11-18): a migration's UPDATE of an 865,000-row table with 104 stored generated
   columns, whose SET list fed none of them, grew ExecutorState to 71.7 GB in 8,612 blocks over 17 minutes on 19rc1
   (pg_log_backend_memory_contexts: Grand total 72.76 GB, every other context small), and was cancelled before the
   64 GiB instance ran out of memory. With one more assignment, a column a cheap generated column reads assigned its
   own value, it completed in 132.7 s at 9.05 MB.
