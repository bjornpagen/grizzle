NOTES: generated-domain-check-partition-routing

What it is
  PostgreSQL refuses, with 42804 "attribute 3 of type record has wrong type / Table has type integer, but query
  expects d_int", an INSERT routed through a partitioned table when a CHECK constraint, an index expression, an index
  predicate or a row security WITH CHECK reads a stored generated column whose type is a domain. The same INSERT into
  a plain table, or straight into the partition, succeeds, and so do COPY, MERGE ... INSERT and a row-moving UPDATE
  through the partitioned table. Since 7c87284940 (2025-04-15, back-patched to 14), expand_insert_targetlist() fills
  an omitted generated column with a NULL Const of the domain's base type. The plan's virtual slot, whose descriptor
  is built from that target list, then reaches ExecInsert() unconverted, because a partitioned table's ri_newTupleSlot
  is virtual too and a partition made with PARTITION OF needs no conversion map. The partition's CHECK then reads g
  from a slot that says integer where the Var says d_int (EVIDENCE.txt 1). It is a bug, present on 19rc1, 19rc2 and
  18.6, and on master by the source.

What is verified and what is not
  Verified by running (EVIDENCE.txt 2 to 4), on stock 19rc1, grizzle's 19rc2 pin and Ubuntu's 18.6:
  - every refusal and acceptance repro.sql lists, with identical output on all three;
  - EXPLAIN VERBOSE's "NULL::integer" for the d_int column;
  - the backtrace, ExecInsert -> ExecConstraints -> ExecCheck -> CheckExprStillValid -> CheckVarSlotCompatibility;
  - that a partition whose columns stand in another order, which routing converts into its own slot, is accepted.
    This confirms the reading's routing step.
  Verified by reading the source (REL_19_RC2, and master 81b2179b49 where EVIDENCE.txt 1 says so):
  - the chain from preptlist.c to CheckVarSlotCompatibility, EVIDENCE.txt 1 a to f;
  - why a plain table escapes: its buffer heap slot differs from the plan's virtual slot, which forces a copy into a
    slot of the relation's type;
  - 7c87284940's change, its back-patch commits and the release tags holding them (GitHub's compare).
  MULTICORE's reading was right in substance. Its line range was preptlist.c:457-469, and the branch is 457-471. It
  did not say why only a partitioned table fails; that is ExecGetInsertNewTuple's slot-ops test (EVIDENCE.txt 1 d).
  Not verified:
  - That releases before 7c87284940 (17.4, 16.8, 15.12, 14.17) accept the INSERT. No such build was run. It is
    inferred from the source, where the entry was a CoerceToDomain, or a Const of the domain type, either way typed
    as the column.
  - That 17.5+, 16.9+, 15.13+ and 14.18+ refuse it. None was run. Their back-patches change the same lines.
  - The proposed diff: unbuilt, untested, and no regression suite run, because of the machine's CPU freeze.
  - MULTICORE's count of edullm's affected CHECKs and columns (below), which was not recounted here.

How grizzle met it
  Lane MULTICORE, measuring a partitioned representation of edullm's tables, met the refusal on an INSERT through the
  partitioned parent. grizzle types a generated field by a domain, and a law's CHECK reads it through a cast to the
  base type, as in repro.sql's last case: a bit(16) domain and CHECK (g::"bit" = B'0000000000000001' OR x <= 0).
  MULTICORE counts 13 such CHECKs on 9 of edullm's tables, reading 32 domain-typed generated columns.

What grizzle does instead
  Nothing yet. The partitioned representation is not adopted, and those 9 tables stay unpartitioned while it is open.
  Ways round it, none adopted:
  - insert into the partition directly, routing on the host;
  - write through MERGE or COPY, which build a slot of the relation's own type;
  - type the generated columns by their base types.
  When this is fixed upstream and the pin moves past the fix, the partitioned representation is unblocked for them.

The fix proposed
  proposed-generated-null-column-type.diff, against master 81b2179b49. It also applies to REL_19_RC2.
  - expand_insert_targetlist() keeps 7c87284940's bare NULL Const, with no CoerceToDomain, so a NOT NULL domain is
    still never checked against a placeholder that ExecComputeStoredGenerated() overwrites.
  - The Const is labelled with the column's own type and typmod, not the base type's. The plan's output then has the
    relation's types, as before 7c87284940, and the routed slot matches the Vars that read it.
  - ExecCheckPlanOutput()'s comment follows, and its check is unchanged: any NULL Const.
  - utils/lsyscache.h, which 7c87284940 included for getBaseTypeAndTypmod, is then unused in preptlist.c. The diff
    leaves it, since an unbuilt diff can't show that dropping it compiles.
  - An alternative on the executor side: ExecInitInsertProjection decides, once, whether the plan's descriptor
    matches the relation's, and ExecGetInsertNewTuple copies whenever it doesn't. That would also cover the INT4 NULL
    of a dropped column, which no expression reads. The planner fix is the smaller change, and it puts back the type
    the plan had before.
