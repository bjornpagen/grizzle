EVIDENCE: gistcostestimate() costs a GiST scan by the selectivity of all its quals, whichever columns they constrain

Run 2026-11-04. Machine: Darwin 27.0.0 arm64 (macOS 27.0.1), VirtualMac2,1, Apple M2 Max (virtual), 10 cores, 64 GB.
The cores were shared with other work, so times are indicative only. Buffer counts and estimated costs are exact and
are what matter. Each statement in repro.sql runs twice, and the second, warm run is quoted.

4. THE ARITHMETIC (defaults: random_page_cost 4.0, cpu_index_tuple_cost 0.005, cpu_operator_cost 0.0025)
   2a and 2b, at N = 100000. room = 2186 is estimated at 20 rows, and there is one qual (qual_op_cost 0.0025).
                                 GiST (during, room), 892 pages        B-tree (room), 140 pages
     numIndexTuples              20 (every qual)                       20 (bound quals: room = 2186)
     numIndexPages               ceil(20 * 892 / 100000) = 1           ceil(20 * (140 - 1) / 100000) = 1
       x random_page_cost        4.0                                   4.0
     tuples x (0.005 + 0.0025)   0.15                                  0.15
     descent comparisons         ceil(ln 100000) = 12   -> 0.03        ceil(log2 100000) = 17   -> 0.0425
     descent pages x 0.125       (int) log100(892) = 1, 2 -> 0.25      height 1, 2              -> 0.25
     index cost                  4.43       (EXPLAIN 4.43)             4.4425     (EXPLAIN 4.44)
     index pages read            892                                   2
   - The heap side of the two plans depends on the selectivity and the heap only, so it adds the same to both.
   - The plan totals, 75.39 against 75.41, carry the same 0.0125 = (17 - 12) * 0.0025.
   - GiST (room, during), 655 pages, follows the same arithmetic as (during, room): 4.43, with 3 pages read (2c).
   - In the slotted index, 1087 pages, (int) log100(1087) = 1, so both lookups cost 4.43, reading 3 and 1087 pages (2f).
   - In kinded, 804 pages, the lookup on room costs 4.43 too, and reads 5 pages (2g).

   2e, the range of 10 rooms, estimated 193 rows, two quals (qual_op_cost 0.005):
     GiST:    ceil(193 * 892 / 100000) = 2 pages -> 8.0 + 193 * 0.01 = 1.93 + 0.03 + 0.25 = 10.21   (EXPLAIN 10.21)
     B-tree:  ceil(193 * 139 / 100000) = 1 page  -> 4.0 + 1.93 + 0.0425 + 0.25        = 6.2225  (EXPLAIN 6.22)
   - So the B-tree wins once the GiST index's pro-rata count passes one page, here at about 100000 / 892 = 112 rows.
   - Below that, any lookup on a later GiST column ties with the B-tree at one page, and the descent terms decide in
     GiST's favour.

   2i, at N = 1000000 (estimated 21 rows):
     GiST, 8928 pages:   4.0 + 21 * 0.0075 = 0.1575 + ceil(ln 1e6) = 14 -> 0.035 + ((int) log100(8928) = 1) + 1 -> 0.25
                         = 4.4425   (EXPLAIN 4.44)
     B-tree, 1204 pages: 4.0 + 0.1575 + ceil(log2 1e6) = 20 -> 0.05 + (height 2) + 1 = 3 -> 0.375
                         = 4.5825   (EXPLAIN 4.58)
   - The gap is 0.14: 0.015 from ln against log2 and 0.125 from the height terms.
   - The B-tree's height of 2 is the one value the cost 4.58 admits; pageinspect's bt_metap was not run.
   - So making the comparison count log2, as in the 2024 diff (section 6), would close 2a but not 2i.

   2d, a search by span with 1 row estimated:
     both GiST indexes:  1 page -> 4.0 + 0.0075 + 0.03 + 0.25 (heights (int) log100(655) = (int) log100(347) = 1)
                         = 4.2875, plus the heap's 4.0 and 0.01: 8.30 each
   - The indexes differ in size by nearly half, and the estimates still tie exactly. The page count enters only
     through the one-page rounding and the truncated log100.
