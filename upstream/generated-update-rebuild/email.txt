Hi,

This thread stalled in March and nothing was committed, so 18.0
through 18.7, 19.0 and master still initialize the generated columns
again for every row of such an UPDATE.  We hit it independently: a
schema migration of ours updated 865,000 rows of a table with 104
stored generated columns, assigning only columns none of them reads,
and ExecutorState reached 72 GB before we cancelled it.

Tom Lane <tgl@sss.pgh.pa.us> writes:
> I don't like using ri_extraUpdatedCols_valid here: it requires callers
> to know more than they should about how ExecInitGenerated works, and
> it does not fix the comparable performance problem that probably
> exists in the INSERT path.  I think the right fix is to have three
> booleans specifically reflecting the validity of ri_GeneratedExprsU,
> ri_GeneratedExprsI, and ri_extraUpdatedCols.

Matthias, for his part, would rather not add fields in the back
branches, even in padding.  The attached v3 takes a third way, which I
think meets both concerns: ExecInitGenerated() keeps its array even
when no column needs computing, as ExecInitStoredGenerated() did
before 83ea6c54025, instead of freeing it and storing NULL.  A NULL
ri_GeneratedExprsU or ri_GeneratedExprsI then again means only that
ExecInitGenerated() hasn't run for that command type, alike for UPDATE
and INSERT, so ExecComputeStoredGenerated() goes on testing the very
field it is about to use and needs to know nothing more.  Nothing is
added to ResultRelInfo, and the same patch applies to master,
REL_19_STABLE and REL_18_STABLE.  The cost is one array of natts
pointers per result relation, kept where it used to be freed.

v3 also makes the UPDATE branch's "Don't call twice" assertion test
ri_extraUpdatedCols_valid, which ExecInitGenerated() sets whenever it
runs for UPDATE.  The existing one tests the array, which the bug
leaves NULL, so it could not fire.  The new test in
generated_stored.sql (mirrored in generated_virtual.sql) updates
several rows without touching what the generated column reads, by
UPDATE, INSERT ... ON CONFLICT DO UPDATE, MERGE, an UPDATE with a
statement-level BEFORE UPDATE trigger (which reaches
ExecInitGenerated() first, through ExecGetAllUpdatedCols()), and an
UPDATE of a partitioned table.  On an assert-enabled build with the
new assertion but without the fix, it fails:

  TRAP: failed Assert("!resultRelInfo->ri_extraUpdatedCols_valid"), File: "nodeModifyTable.c", Line: 536

No existing regression test reaches a second call.  I don't see a way
to test the memory itself in the regression suite.

To reproduce (psql -X, as a superuser for pg_backend_memory_contexts):

  SELECT format('CREATE TABLE t (a int, b int, g int GENERATED ALWAYS AS '
                '(CASE WHEN a IN (%s) THEN 1 ELSE 0 END) STORED)',
                string_agg(i::text, ', '))
  FROM generate_series(0, 999) AS i \gexec
  INSERT INTO t (a, b) SELECT i, i FROM generate_series(1, 40000) AS i;
  CREATE FUNCTION probe() RETURNS trigger LANGUAGE plpgsql AS $$
  BEGIN
    RAISE NOTICE 'ExecutorState: % bytes', (SELECT max(total_bytes)
      FROM pg_backend_memory_contexts WHERE name = 'ExecutorState');
    RETURN NULL;
  END $$;
  CREATE TRIGGER probe AFTER UPDATE ON t
    FOR EACH STATEMENT EXECUTE FUNCTION probe();
  \timing on
  UPDATE t SET b = b + 1;         -- g doesn't read b
  UPDATE t SET a = a, b = b + 1;  -- g reads a

On master (5c06a7ef24c), with the backend's CPU time from
log_statement_stats:

                                   ExecutorState       CPU
  unpatched  SET b = b + 1         3238002688 bytes    16.47 s
             SET a = a, b = b + 1      262144 bytes    0.145 s
  v3         SET b = b + 1             131072 bytes    0.052 s
             SET a = a, b = b + 1      262144 bytes    0.145 s

Unpatched, the first statement takes about 81 kB per row at 10,000,
20,000 and 40,000 rows alike, and so does the same SET list through
INSERT ... ON CONFLICT DO UPDATE, MERGE, or an UPDATE of a partitioned
table; with v3 all of them stay flat.  REL_18_STABLE and REL_19_STABLE
give the same numbers byte for byte, and 83ea6c54025's parent is flat.

Tested: meson test, every suite, TAP tests included, on assert-enabled
builds of master, REL_19_STABLE and REL_18_STABLE with v3 applied,
with no failures.  pgindent leaves nodeModifyTable.c unchanged.
