EVIDENCE: an UPDATE that assigns no column a stored generated column reads initializes the table's generation
expressions again for every row, in the per-query context

Run 2026-11-18 on aarch64-linux (Ubuntu 26.04, gcc 15.2.0), each build in its own throwaway cluster (Unix socket only,
fsync off), repro.sql under psql -X as the bootstrap superuser:
  - PostgreSQL 18.6 (Ubuntu 18.6-0ubuntu0.26.04.1), the distribution's package.
  - PostgreSQL 19rc1 (REL_19_RC1), stock: RC1TARGET's build, no patches.
  - PostgreSQL 19rc2 (REL_19_RC2, dffcca2e3c) with grizzle's three source patches (scripts/pg/pin.env). One of them,
    relcache-planned-check-and-generation, makes RelationGetGenerationExpr() return the relcache's tree, so this build
    shows what is left once the tree is not parsed again: the bitmap pull_varattnos() builds.

1. THE CAUSE, IN THE SOURCE (line numbers are REL_19_RC2's, dffcca2e3c; the same code on REL_18_STABLE and master as
   read on GitHub on 2026-11-18; REL_17_STABLE's ExecInitStoredGenerated() has no such block and always keeps its
   array, so 17 does not do this)
   a. src/backend/executor/nodeModifyTable.c, ExecInitGenerated(), line 477 switches to estate->es_query_cxt; for each
      stored generated column, line 491 calls build_column_default() (stringToNode() of adbin), and line 504
      pull_varattnos(), to skip a column no UPDATE target column feeds.
   b. Lines 525-530: when no column is needed, "didn't need it after all", the array is pfree'd and
      ri_GeneratedExprs = NULL is what lines 536-539 store in ri_GeneratedExprsU, with ri_NumGeneratedNeededU = 0 and
      ri_extraUpdatedCols_valid = true.
   c. ExecComputeStoredGenerated(), line 581: if (resultRelInfo->ri_GeneratedExprsU == NULL) ExecInitGenerated(...),
      then line 583 returns early because ri_NumGeneratedNeededU == 0. ExecUpdatePrepareSlot() calls it for every row
      of a table with a stored generated column, so on every row (a) runs again. The "Don't call twice" Assert at
      line 536 tests the same NULL and so does not fire.
   d. Nothing frees what (a) allocates in es_query_cxt until ExecutorEnd: the parsed tree of every stored generated
      column (with build_column_default()'s coercions) and its attrs_used bitmap, per row.

2. MEASUREMENTS (repro.sql: one stored generated column whose expression is a 1,000-element IN list; ExecutorState
   read by a statement-level AFTER UPDATE trigger, which runs in AfterTriggerEndQuery before ExecutorEnd)

   PostgreSQL 18.6 and 19rc1, identical:
      statement            | rows  | executor_state_bytes | bytes_per_row
      SET a = a, b = b + 1 |  2000 |               262144 |           131
      SET a = a, b = b + 1 |  8000 |               262144 |            32
      SET a = a, b = b + 1 | 32000 |               262144 |             8
      SET b = b + 1        |  2000 |            167772160 |         83886
      SET b = b + 1        |  8000 |            654311424 |         81788
      SET b = b + 1        | 32000 |           2592079872 |         81002
   and, on 19rc1, 32,000 rows: SET b = b + 1 13.4 s, SET a = a, b = b + 1 0.76 s.

   19rc2 with the relcache patch (the tree cached, the bitmap still built):
      SET a = a, b = b + 1 |  2000 |                49200 |            24
      SET a = a, b = b + 1 | 32000 |                49200 |             1
      SET b = b + 1        |  2000 |                65536 |            32
      SET b = b + 1        | 32000 |              1048576 |            32

3. IN THE FIELD: a migration's UPDATE of an 865,000-row table with 104 stored generated columns, whose SET list fed
   none of them, grew ExecutorState to 71.7 GB in 8,612 blocks over 17 minutes on 19rc1
   (pg_log_backend_memory_contexts: Grand total 72.76 GB, every other context small) and was cancelled before the
   instance, 64 GiB, ran out of memory. The same UPDATE with one more assignment, a column one cheap generated column
   reads, assigned its own value, holds ExecutorState flat.
